# معماری — کیان بهساز

این سند تصمیم‌های معماری و **دلیل** هرکدام را ثبت می‌کند. هدف این است که وقتی
شش ماه بعد کسی می‌خواهد چیزی را عوض کند، بداند آن تصمیم چه چیزی را نگه می‌داشت.

---

## ۱. تصویر کلی

```
                         Internet
                            │
                     Cloudflare  (DNS · CDN · WAF · TLS · Rate limit)
                            │
                          Nginx   (TLS مبدأ · Rate limit · فایل‌های media)
                            │
              ┌─────────────┴─────────────┐
              │   Next.js (یک پراسس)      │
              │                           │
              │   سایت عمومی   +   Payload CMS
              │   (App Router)     (/admin)
              └─────────────┬─────────────┘
                            │
                       PostgreSQL
                    ┌───────┴───────┐
                    │ schema: cms   │  محتوا (Payload / Drizzle)
                    │ schema: app   │  داده عملیاتی (Prisma)
                    └───────────────┘
```

### چرا CMS یک سرویس جدا نیست

در طرح اولیه، CMS یک باکس مستقل کنار Next.js بود. Payload 3 داخل خود Next.js
اجرا می‌شود و این تفاوت، چند چیز را حذف می‌کند:

- **بدون رفت‌وبرگشت HTTP:** صفحات با Local API مستقیم به دیتابیس می‌روند
  (`src/lib/cms/client.ts`). یک شبکه‌هاپ کمتر در مسیر رندر یعنی TTFB کمتر.
- **بدون وبهوک برای کش:** هوک‌های `afterChange` مستقیماً `revalidateTag` را
  صدا می‌زنند (`src/payload/hooks/revalidate.ts`). پنجره‌ای وجود ندارد که ادمین
  ذخیره کرده باشد و سایت هنوز نسخه قبلی را نشان دهد.
- **یک دیپلوی، یک نسخه:** تایپ‌های CMS و کد سایت هرگز از هم جلو نمی‌افتند.

هزینه‌اش این است که ادمین و سایت یک پراسس را شریک‌اند. اگر روزی بار پنل ادمین
مسئله شد، Payload می‌تواند به یک سرویس جدا منتقل شود؛ لایه `src/lib/cms/` تنها
جایی است که باید تغییر کند، چون همه صفحات فقط از آن استفاده می‌کنند.

## ۲. چندزبانگی

`src/lib/i18n/config.ts` تنها منبع حقیقت است: مسیریابی، `hreflang`، تعویض زبان،
Localization سمت CMS و sitemap همه از همان آرایه مشتق می‌شوند.

**تصمیم کلیدی: اسلاگ ترجمه نمی‌شود.** یک محصول یک سند است با یک `slug` و
فیلدهای محتوایی localize شده. نتیجه:

```
/fa/products/brick-x
/en/products/brick-x
/ar/products/brick-x
```

هر سه یک سند هستند. به همین دلیل:

- `hreflang` بدون جدول نگاشت ساخته می‌شود (`src/lib/seo/metadata.ts`).
- تعویض زبان فقط همان مسیر را در locale دیگر باز می‌کند
  (`src/components/layout/LocaleSwitcher.tsx`) و کاربر روی همان صفحه می‌ماند.
- `generateStaticParams` یک بار اسلاگ‌ها را می‌خواند و برای هر سه زبان استفاده می‌کند.

اگر روزی اسلاگ ترجمه‌شده لازم شد (مثلاً `/fa/products/آجر-نما`)، این تصمیمی است
که باید آگاهانه شکسته شود: نیاز به فیلد `slug` لوکالایزشده، یک lookup معکوس و
بازنویسی تعویض زبان دارد.

**جهت متن:** `dir` روی `<html>` از locale می‌آید و کل UI با property‌های منطقی
Tailwind (`ms-`, `pe-`, `start-`, `text-start`) نوشته شده، نه `left/right`.
بنابراین RTL یک استایل جداگانه نیست.

## ۳. مدل محتوا

| Collection | نقش |
| --- | --- |
| `products` + `product-categories` | محصولات، مشخصات فنی، کاربردها، دانلودها |
| `projects` + `project-categories` | پروژه‌ها با کارفرما/موقعیت/سال و محصولات به‌کاررفته |
| `articles` + `article-categories` | مقالات و پایگاه دانش |
| `pages` | صفحات متنی (حریم خصوصی، شرایط استفاده، …) |
| `media` | تصاویر، با سایزهای از پیش ساخته‌شده |
| `catalogs` | فایل‌های PDF قابل دانلود |
| `users` | حساب‌های CMS با نقش `admin` / `editor` |

| Global | نقش |
| --- | --- |
| `site-settings` | هویت، اطلاعات تماس، شبکه‌های اجتماعی، آمار صفحه اصلی |
| `home-page` | Hero و روشن/خاموش کردن بخش‌های صفحه اصلی |
| `careers` | موقعیت‌های شغلی |

سه دسته‌بندی از یک factory ساخته می‌شوند (`src/payload/collections/categories.ts`)
تا با گذر زمان از هم دور نیفتند.

**چرا `status` علاوه بر draft:** یک فیلد صریح `published/draft` باعث می‌شود لایه
داده عمومی با یک شرط ساده فیلتر کند، و ویراستار بتواند بدون حذف، یک سند را از
انتشار خارج کند.

**فرم‌ها در CMS نیستند.** درخواست‌های تماس در اسکیمای `app` و با Prisma ذخیره
می‌شوند، نه به‌عنوان یک Collection. دلیلش دسترسی است: یک حساب editor که برای
ویرایش محتوا ساخته شده نباید بتواند لیست سرنخ‌های فروش را بخواند.

## ۴. دو ORM روی یک دیتابیس

| مالک | اسکیما | ابزار | داده |
| --- | --- | --- | --- |
| Payload | `cms` | Drizzle (داخلی Payload) | محتوا |
| اپلیکیشن | `app` | Prisma | `contact_requests`, `newsletter_subscribers`, `audit_log` |

هر کدام فقط اسکیمای خودش را مهاجرت می‌کند، پس هیچ‌کدام نمی‌تواند جدول دیگری را
خراب کند. چون یک دیتابیس است، یک `pg_dump` هم محتوا و هم داده عملیاتی را می‌گیرد.

قیمتش: دو ابزار مهاجرت در خط دیپلوی (`prisma migrate deploy` و `payload migrate`).

## ۵. کش و بازاعتبارسنجی

```
درخواست → صفحه (ISR)
             └→ src/lib/cms/queries.ts  (unstable_cache با tag)
                                           ▲
             ذخیره در پنل ادمین ───────────┘  revalidateTag
```

- هر خواننده در `queries.ts` با یک tag کش می‌شود که نام آن دقیقاً slug همان
  collection است (`src/lib/cms/tags.ts`)، پس اضافه‌کردن collection جدید نمی‌تواند
  بی‌سروصدا invalidation را فراموش کند.
- `revalidate` روی صفحات فقط تور ایمنی است؛ مسیر اصلی، purge مستقیم هوک است.
- `POST /api/revalidate` برای مواردی است که خارج از Payload اتفاق می‌افتد
  (بازیابی بکاپ، ایمپورت انبوه). با هدر `x-revalidate-secret` و مقایسه
  timing-safe محافظت می‌شود.

**یک تله که برطرف شده:** `generateStaticParams` عمداً از کش استفاده **نمی‌کند**
(`getPublishedSlugs` / `getCategorySlugs`). `unstable_cache` بین بیلدها در
`.next/cache` باقی می‌ماند؛ اگر لیست اسلاگ‌ها کش می‌شد، یک محصول تازه‌منتشرشده تا
انقضای آن ورودی از مجموعه پیش‌رندرشده بیرون می‌ماند.

**مقیاس:** rate limiter در حافظه پراسس است (`src/lib/security/rate-limit.ts`).
برای یک کانتینر کافی است. با بیش از یک اینستنس باید به Redis منتقل شود — همان‌طور
که فایل‌های media باید به object storage بروند.

## ۶. عملکرد

هدف: `LCP < 2.5s`، `INP < 200ms`، `CLS < 0.1`.

چیزهایی که در معماری تضمین می‌شوند، نه در بازبینی بعدی:

- **Server Components به‌صورت پیش‌فرض.** فقط پنج کامپوننت `'use client'` دارند:
  فرم تماس، خبرنامه، منوی موبایل، تعویض زبان، گالری/مودال.
- **Hero.** تصویر موبایل و دسکتاپ جدا هستند، تصویر `priority` است و `sizes`
  صریح دارد، و متن Hero هرگز انیمیشن نمی‌شود. ویدیو فقط از breakpoint `md` به
  بالا پخش می‌شود — روی دیتای موبایل هرگز.
- **تصاویر.** Payload هنگام آپلود سایزهای `thumbnail/card/wide/og` را می‌سازد و
  خروجی WebP است؛ هیچ تغییر اندازه‌ای در زمان درخواست انجام نمی‌شود. Next هم
  AVIF/WebP سرو می‌کند.
- **فونت.** یک خانواده (Vazirmatn) برای هر سه زبان، با `next/font` و
  `display: swap`. تعویض زبان، تعویض فونت نیست.
- **انیمیشن.** یک کامپوننت `Reveal` با جابه‌جایی ۱۶ پیکسلی که با
  `prefers-reduced-motion` کاملاً غیرفعال می‌شود. هیچ‌چیز بالای fold انیمیشن ندارد،
  پس انیمیشن نمی‌تواند روی LCP اثر بگذارد.
- **Pagination با لینک واقعی** (`?page=`)، نه «بارگذاری بیشتر» — هم قابل ایندکس
  است هم JavaScript کمتری می‌خواهد.

## ۷. SEO

همه چیز از `src/lib/seo/` می‌آید:

- `buildMetadata()` تنها ورودی metadata صفحه است. اولویت: override‌های CMS →
  مقادیر خود صفحه → پیش‌فرض‌های سایت.
- `buildAlternates()` برای هر صفحه هر سه زبان به‌علاوه `x-default` را اعلام می‌کند.
- `sitemap.ts` مسیرهای ثابت و محتوای CMS را در هر سه زبان، همراه با
  alternate‌ها، تولید می‌کند. اسنادی که `seo.noIndex` دارند حذف می‌شوند.
- `robots.ts` اگر origin دقیقاً دامنه پروداکشن نباشد، **کل سایت را disallow
  می‌کند** — تا یک استیجینگ هرگز ایندکس نشود.
- JSON-LD: `Organization` و `WebSite` در layout، `BreadcrumbList` از همان آرایه‌ای
  که breadcrumb را رندر می‌کند، به‌علاوه `Product` و `Article` در صفحات جزئیات.
  خروجی با escape کردن `<` رندر می‌شود تا متن CMS نتواند از تگ `<script>` فرار کند.

## ۸. امنیت

| لایه | کار |
| --- | --- |
| Cloudflare | WAF، محدودسازی نرخ لبه، TLS |
| Nginx | TLS مبدأ، zoneهای rate limit جدا برای فرم‌ها و `/admin`، `real_ip` فقط از رنج‌های Cloudflare |
| Next.js | هدرهای امنیتی و CSP در `next.config.ts` |
| API | اعتبارسنجی Zod، rate limit، honeypot، هش IP |
| Payload | کنترل دسترسی مبتنی بر نقش، قفل حساب پس از ۵ تلاش ناموفق |
| PostgreSQL | روی هاست publish نمی‌شود؛ فقط شبکه داخلی compose |

نکات مشخص:

- **CSP** برای سایت عمومی اعمال می‌شود و `/admin` و `/api/cms` از آن مستثنا
  هستند، چون پنل ادمین به inline style/script متکی است. `frame-ancestors 'none'`
  همه‌جا برقرار است.
- **honeypot** یک فیلد مخفی است که ربات‌ها پر می‌کنند. اگر پر باشد، سرور **۲۰۰
  برمی‌گرداند و چیزی ذخیره نمی‌کند** — ربات از پاسخ چیزی یاد نمی‌گیرد.
- **IP هش می‌شود** با `SHA-256(ip + IP_HASH_SALT)` پیش از ذخیره. برای تشخیص سوء‌استفاده
  کافی است، برای شناسایی مجدد کافی نیست، و چرخاندن salt سابقه را غیرقابل‌پیوند می‌کند.
- **نقش کاربر** فیلدی است که فقط admin می‌تواند بنویسد، پس editor نمی‌تواند خودش
  را ارتقا دهد.
- **لاگ خطا** هرگز محتوای ارسالی فرم را چاپ نمی‌کند.
- **Secretها** فقط از environment می‌آیند. `prisma.config.ts` باعث شده URL
  دیتابیس حتی در فایل schema هم نباشد.

## ۹. دیزاین سیستم

توکن‌ها در `src/styles/globals.css` با `@theme` تعریف می‌شوند (Tailwind v4،
پیکربندی CSS-first — به همین دلیل `tailwind.config.ts` وجود ندارد). هر توکن هم
utility می‌سازد هم CSS variable، پس دو منبع حقیقت وجود ندارد.

- پالت: `brand` (گرافیت/فولادی، رنگ سازه‌ای سایت) و `accent` (رس پخته، فقط برای
  CTA و یک جزئیات در هر بخش).
- ریتم عمودی فقط از `Section` می‌آید؛ صفحات padding خودشان را تعریف نمی‌کنند.
- `MediaCard` مشترک محصولات، پروژه‌ها و مقالات است تا سه لیست با رشد سایت از هم
  دور نشوند.

## ۱۰. عملیات

**بکاپ.** یک `pg_dump` هر دو اسکیما را می‌گیرد. برنامه پیشنهادی: روزانه با نگهداری
۷ روز، هفتگی با نگهداری ۸ هفته، و یک نسخه off-site. بازیابی باید حداقل فصلی تمرین
شود؛ بکاپی که بازیابی‌اش تست نشده، بکاپ نیست.

**مهاجرت‌ها.** همیشه پیش از سوئیچ به نسخه جدید:

```bash
npx prisma migrate deploy
npx payload migrate
```

**فایل‌های media** روی volume کانتینر هستند. این تنها چیزی است که مانع اجرای
بیش از یک اینستنس اپلیکیشن می‌شود؛ قدم بعدی انتقال آن‌ها به S3/R2 است
(`@payloadcms/storage-s3`).

**ایمیل.** هنوز adapter ایمیل تنظیم نشده، پس Payload ایمیل‌ها را در کنسول
می‌نویسد. پیش از راه‌اندازی «فراموشی رمز عبور» یا اعلان فرم تماس، باید یک adapter
اضافه شود.

## ۱۱. کارهای باقی‌مانده (عمدی)

این‌ها آگاهانه انجام نشده‌اند و نقشه راه مرحله بعد هستند:

1. **Adapter ایمیل** — برای بازیابی رمز و اعلان فرم تماس.
2. **Object storage برای media** — پیش‌نیاز اجرای چنداینستنسی.
3. **Rate limit روی Redis** — پیش‌نیاز اجرای چنداینستنسی.
4. **تست‌ها** — تست واحد برای `lib/` و یک تست e2e برای مسیر فرم تماس.
5. **صفحه جست‌وجو** — با توجه به سه‌زبانه بودن، احتمالاً Postgres full-text با
   پیکربندی جداگانه برای هر زبان.
6. **پنل مشتری** — در معماری فعلی به‌عنوان یک route group جدید و یک مجموعه
   جدول در اسکیمای `app` جا می‌گیرد؛ چیزی در طراحی فعلی مانع آن نیست.
